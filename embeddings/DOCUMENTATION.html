1Overview

The extractor and builder produce one record per 3GPP specification version, each paired with the clean full text of that version. embed_cparas.py reads those records, cuts every version's text into clause-aware chunks, sends the chunks to an embedding model, and stores one vector per chunk together with the chunk's text and metadata. The result supports semantic search ("which clause describes UE behaviour on radio link failure?") filtered by specification, series, release or chunk kind.

What goes in

The builder's output folder, the extractor's output folder, a single etsi_dataset.zip, the split etsi_dataset_partNN.zip files, or etsi_dataset.jsonl with its text/ folder. Read only; the tool refuses an output folder that overlaps the dataset.

What comes out

embeddings.npy (float32, one row per chunk, L2-normalised) and chunks.jsonl (line N describes row N), plus a commit log, a settings manifest and run reports. Optional faiss.index and a Chroma collection.

Design goals, in order: never corrupt or mix data (one store = one model and one chunking; crash-safe commits); never touch the source dataset; spend model time only on text that has not been embedded before; keep every vector traceable to an exact spec version, clause and character range.

2Where it fits in the pipeline

The embedding step is a new branch after the builder. It does not replace the existing import into CPARAS ISLD and the Platform; it reads the same etsi_dataset.zip those importers use.

3Quick start

pip install -r requirements.txt            # numpy
ollama pull nomic-embed-text               # default embedding model

# 1. dry run: chunk everything and report counts (no model needed, writes only dryrun_report.json)
python embed_cparas.py embed --dataset D:\3gpp\build_v2 --out D:\3gpp\vectors --dry-run

# 2. trial on a few documents, to see speed and output
python embed_cparas.py embed --dataset D:\3gpp\build_v2 --out D:\3gpp\vectors_test --series 55 --limit 5

# 3. full run (resumable: run the same command again after Ctrl+C or a crash)
python embed_cparas.py embed --dataset D:\3gpp\build_v2 --out D:\3gpp\vectors

# 4. search, and check the store
python embed_cparas.py query --out D:\3gpp\vectors "UE behaviour on radio link failure" -k 5 --release 16
python embed_cparas.py validate --out D:\3gpp\vectors --dataset D:\3gpp\build_v2

The first word after the script name is the command; if it is omitted, embed is assumed.

4Architecture

The tool is a single-process streaming pipeline. Documents are read one at a time; their chunks flow through a de-duplication router into batches for the model; finished documents are committed to the store strictly in dataset order. Memory use is bounded by the batch size and the handful of documents waiting for their last vectors, not by the size of the dataset.

5What happens during a run

  1. Settings. The command line is turned into a configuration (backend, model, prefixes, chunk sizes, flags). Its hash is compared with manifest.json in --out; a mismatch stops the run before anything is written.
  2. Safety checks. --out must not be inside the dataset folder or its text folder, nor contain them.
  3. Store opening and repair. docs.jsonl is read up to its last complete line. That gives the number of committed rows, the set of committed document ids with their fingerprints, and the map from embedding key to row. chunks.jsonl and embeddings.npy are truncated to exactly that many rows (see section 8).
  4. Backend check. For Ollama: the server answers and the model is pulled. Otherwise a clear message and exit code 1.
  5. Streaming. For each record: skip it if unreadable, filtered by --series/--specs, a repeated document_id, or already committed with the same fingerprint. A committed id whose fingerprint differs is counted as changed_since_embedded and left untouched.
  6. Chunk and route. The record is chunked, each chunk gets its embedding input and key, and the router either reuses an existing vector or queues the input in the current batch. A full batch is sent at once.
  7. Commit. After every batch and every document, the queue commits all leading documents that have every vector. A document that lost an input to a rejection is written to failed.jsonl instead; it is not in docs.jsonl, so the next run retries it.
  8. Finish. The last partial batch is sent, remaining documents are committed, and embed_report.json is written. If requested, FAISS and Chroma exports run.

Progress is printed to the console every 30 seconds (documents read, embedded, chunks, model inputs per second).

6Chunking

Retrieval quality depends more on chunking than on almost anything else. A chunk should be about one idea, carry enough context to be understood alone, and be traceable to its clause. The chunker works on the full extracted text (not on the 700-character clause excerpts in the record) and uses the record's clause tree as a guide.

Rules

  1. Find headings. A line is a clause heading only if it starts with a clause number from the record's own clauses list, followed by whitespace and a title, and (when the tree has a title) the line's title starts with the same first 8 letters and digits. Each number is used once, at its first qualifying line. This rejects table rows, list items and cross-references that happen to start with a number. CRLF line endings are normalised to LF first.
  2. Sections. Text before the first heading is a preamble; each heading starts a section that runs to the next heading.
  3. Merge forward. A section with fewer than --min-chars (200) characters is glued to the next one. The merged unit is attributed to the later clause and lists all of them in clauses_covered.
  4. Split. Each unit is cut into pieces of at most --max-chars (1500), breaking at the last paragraph break, else line break, else sentence end (. or ; ), else comma, else space within the window. A tail shorter than --min-chars is absorbed into the previous piece if the result stays within 1.25 × --max-chars. Consecutive pieces overlap by about --overlap (150) characters, aligned to a word start.
  5. Drop strays. Pieces under 40 non-space characters (a lone heading at the end) are dropped and counted.
  6. Summary chunk. Unless --no-summary, one more chunk is built from technical_summary (scope, purpose, summary) and classification (domain, subdomain, topics, protocols, interfaces, network components, key features), if that text is at least 80 characters. These fields were generated by the LLM during extraction, so the chunk is marked "llm_generated": true and kind: "summary".
  7. No clause tree. If the record has no clause list, or none of its headings are found, the whole text is one unit and is split into plain windows with an empty clause.
  8. No text. A record without a text file gets only its summary chunk (and is counted as docs_without_text).

What is actually embedded

The model does not see the bare chunk. It sees:

<document prefix of the model>TS 38.331 Radio Resource Control (RRC); Protocol specification
Clause 5.3.7 RRC connection re-establishment

<chunk text>

The context line lets short clauses ("The UE shall start timer T311.") be found by what they are about. It deliberately leaves out the version, so identical clause text in different releases produces an identical input (see De-duplication). --no-context-header removes the line. The stored text field in chunks.jsonl is always the bare chunk.

Defaults (1500 / 150 / 200 characters) give chunks of roughly 300–400 tokens, comfortably inside the 2048-token context Ollama gives most embedding models by default. If you raise --max-chars a lot, raise --num-ctx too, otherwise Ollama silently truncates the input.

7De-duplication

Consecutive releases of a specification share most of their text. Re-embedding it would multiply the model time by the number of releases kept. The key of a chunk is the SHA-256 of its exact embedding input; before sending an input to the model the router checks, in order:

#Where the vector may already beWhen it happens
1Resolved in memory, its document not committed yetThe same text appears again shortly after, e.g. in the next version, before the previous one finished.
2A committed row of embeddings.npy (read back from disk)Text embedded earlier in this run or in any previous run.
3Already queued in the current batchTwo documents in the same batch share a chunk; the chunk waits for the one request.
4NowhereAdded to the batch and sent to the model.

Reused vectors are still written as their own row with their own metadata, so every version keeps a complete set of rows and a search can be filtered by release. Only model time is saved, not storage. The dry run reports unique_embedding_inputs and saved_by_dedup; the real run reports reused_vectors.

Commit protocol

Each spec version is committed as one unit. The order of writes makes a single line in docs.jsonl the commit marker; anything written after the last marker is, by definition, uncommitted and is cut off at the next start.

If the files are inconsistent in a way that cannot come from an interrupted write (for example chunks.jsonl shorter than the commit log), the tool stops with "store damaged" rather than guessing. Use a new --out or --overwrite.

The settings guard

The settings that change what a vector means are hashed: backend, model, document and query prefixes, normalisation, max_chars, overlap, min_chars, the context line, the summary chunk and the chunker version. Running against an existing store with any of them different is refused and the differences are listed. Vectors from two models live in different spaces; mixing them would make every search silently wrong. Settings that do not change vectors (URL, timeout, batch size, filters) can differ between runs.

Choosing a model

nomic-embed-text is the default because it is small and quick to pull. Other models that work through Ollama include bge-m3, qwen3-embedding and mxbai-embed-large. Compare them on your own data rather than on general benchmarks: embed one or two series into separate stores, run the same 20 or so questions that your users actually ask, and compare the top results. Changing the model later means re-embedding everything, so this comparison is worth doing before the full run.

Prefixes

Many retrieval models were trained with a fixed prefix on documents and a different one on queries, and work noticeably worse without them. The tool picks them from the model name, stores them in the manifest, and the query command uses the stored query prefix automatically.

10Errors, retries and failures

A long run must survive a flaky server and a single bad input without losing work, and must stop rather than mark the whole dataset as failed when the backend is broken.

SituationClassified asWhat happens
Connection refused, timeout, HTTP 408 / 429 / 502 / 503 / 504TransientRetried up to 3 times after 2, 6 and 18 s. If it still fails, the run stops with exit code 3. Committed work is kept.
Any other HTTP error, wrong number of vectors, backend exceptionRejected batchThe batch is split in halves recursively until the bad input is alone.
A single input still rejected, or its vector is empty / NaN / infiniteFailed inputEvery document waiting on that input is marked failed, written to failed.jsonl, and retried on the next run. The rest of the run continues.
25 inputs rejected in a rowBroken backendThe run stops with exit code 3 instead of failing every remaining document.
The model returns a different vector size than the store holdsFatalThe run stops immediately (exit 3). This means the model behind the name changed.
Unreadable JSON line in the datasetDataSkipped and counted as unreadable_lines.
Ctrl+CInterruptAlready committed versions are kept; exit code 130.

11Day-to-day operation

Before the full run

  1. Run --dry-run. Read dryrun_report.json: chunks, unique_embedding_inputs (what the model will actually process), characters_to_embed, vector_store_mb_at_768_dims, and chunking.clauses_located against chunking.clauses_known (how well headings were found).
  2. Run a trial with --limit 20 and read the inputs-per-second figure. Divide unique_embedding_inputs by it for an estimate of the full run.
  3. Spot-check a few lines of chunks.jsonl from the trial: are clauses attributed, do chunks read sensibly?

Adding data

Extract more series, rebuild, then run the same embed command again with the same --out. Versions already in the store are skipped by document_id and fingerprint; new ones are appended, reusing vectors for any text already embedded.

Re-extracted or changed versions

If a version's record or text changed since it was embedded (for example the extractor was improved and re-run), the old vectors are left as they are and the version is counted as changed_since_embedded, with examples in embed_report.json. The store does not delete rows in place. To refresh, embed into a new --out or use --overwrite; either way every vector is recomputed, because reuse only works within one store.

Changing the model or chunk settings

Always use a new --out. The old store keeps working until you switch.

Subsets

--series 36,38 and --specs 38.331,55.241 embed only those. Several subset runs into the same store are fine as long as the settings are the same.

Sizing

One float32 vector of 768 dimensions is 3 KB. Each gigabyte of extracted text gives roughly 750 000 chunks at the default size, so about 2.3 GB of vectors plus a similar size of chunks.jsonl. The dry run gives the exact figure for your dataset.

12Using the vectors

Built-in search

python embed_cparas.py query --out D:\3gpp\vectors "T311 expiry during re-establishment" -k 5
python embed_cparas.py query --out D:\3gpp\vectors "A5/3 key derivation" --series 55 --release 19
python embed_cparas.py query --out D:\3gpp\vectors "paging occasion" --spec 38.304 --kind text --json

The question is embedded with the same backend, model and query prefix recorded in the manifest. Scores are cosine similarity. Filters: --spec, --series, --release (accepts 15 or Rel-15), --kind, each comma-separated.

From Python

import json, numpy as np
from pathlib import Path
import embed_cparas as ec

out = Path(r"D:\3gpp\vectors")
hits = ec.search(out, "UE behaviour on radio link failure", k=5, filters={"spec": ["38.331"], "release": ["16"]})
for h in hits:
    print(h["score"], h["spec"], h["version"], h["clause"], h["text"][:120])

# or directly
X = np.load(out / "embeddings.npy", mmap_mode="r")                 # (rows, dim), normalised
meta = [json.loads(l) for l in open(out / "chunks.jsonl", encoding="utf-8")]
# q = embedding of the question, made with the SAME model and the manifest's query_prefix, normalised
scores = X @ q
top = np.argsort(-scores)[:5]

When embedding a question yourself, use exactly the model and query_prefix from manifest.json. With Ollama: POST /api/embed {"model": "nomic-embed-text", "input": ["search_query: your question"]}.

FAISS and Chroma

python embed_cparas.py export --out D:\3gpp\vectors --faiss hnsw            # pip install faiss-cpu
python embed_cparas.py export --out D:\3gpp\vectors --chroma D:\3gpp\chroma # pip install chromadb

--faiss flat is exact search; hnsw (32 neighbours) is approximate and faster for millions of rows. Both use inner product, which equals cosine because vectors are normalised. The FAISS id is the row number in chunks.jsonl.

The Chroma export upserts every chunk into collection cparas_3gpp (cosine space) with chunk_id as the id, the text as the document and all metadata fields (lists joined with commas). Running it again updates in place without duplicates. Example: col.query(query_embeddings=[q], n_results=5, where={"spec": "38.331"}).

13Validation

python embed_cparas.py validate --out D:\3gpp\vectors --dataset D:\3gpp\build_v2

Prints VALID or INVALID (exit code 0 or 2) and writes validation_report.json. Checks:

  • the .npy header is this tool's and the file size matches rows × dim exactly;
  • docs.jsonl rows are contiguous, each line's key count matches its rows, no document appears twice;
  • every chunks.jsonl line has row equal to its position, chunk ids are unique, no chunk text is empty;
  • row counts agree across embeddings.npy, chunks.jsonl and docs.jsonl;
  • no vector contains NaN or infinity, and all norms are 1 ± 0.001 when normalisation is on;
  • with --dataset: how many dataset versions are not in the store (a warning: filtered, failed or not yet run).

15Testing

cd cparas_embeddings
python -m unittest discover -s tests -v

32 tests, needing only numpy. They run against synthetic records in the builder's exact format and a fake Ollama HTTP server, so no model or GPU is needed. Covered:

  • chunking: exact character offsets, heading detection rejecting a table row that starts with a clause number, merge-forward, overlap, termination on pathological text, CRLF text, records without a clause tree or without text;
  • input layouts: single zip, split part zips, jsonl + text, extractor folder;
  • resume, appending new versions, crash repair of half-written tails in all three files;
  • de-duplication across versions, across runs, and at batch sizes 2, 3, 4, 5 and 7;
  • a rejected input failing only its own version, which succeeds on the next run; the 25-in-a-row stop;
  • refusing changed settings, refusing an output inside the dataset, the dataset left byte-for-byte unchanged;
  • search with filters; the .npy header growing and loading with np.load;
  • Ollama batching, prefixes on documents and queries, the legacy endpoint, model not pulled, server down.

The suite was also checked by deliberately breaking key logic (heading title check, crash repair, in-memory reuse, normalisation, merge-forward, row-count validation, the 25-in-a-row stop) and confirming a test fails each time. Separately, the tool was run on output produced by the real build_cparas_dataset.py, including a legacy 02.06dcs specification, and the FAISS and Chroma exports were exercised.

16Limitations and known gaps

  • Speed with a real model is not yet measured. All tests used the fake server or the hash backend. Measure with a --limit 20 trial on your hardware.
  • Changed versions are not refreshed in place. They are reported; refreshing means a new store.
  • Clause attribution depends on the extracted text. If the extractor wrote a heading differently from the clause tree (for example a reworded title), that clause's text is attributed to the previous clause. chunking.clauses_located versus clauses_known in the reports shows how often this happens.
  • Tables are chunked as text. Large ASN.1 blocks and tables are split like prose; they are searchable but not structured.
  • Filtered search scans chunks.jsonl. Fine up to a few million rows; for heavy interactive use, load the store into Chroma or another database with metadata indexes.
  • Summary chunks reflect LLM output from extraction, so they can be wrong in ways the specification text is not. Filter with --kind text when exact wording matters.
  • Single process. One run uses one backend connection. Run separate --series subsets into separate stores if you need parallel machines.
